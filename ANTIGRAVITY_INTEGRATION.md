# Интеграция Antigravity Manager

Исследование проведено 13 октября 2026 года для установленного Antigravity 2.22.0.0.
Снимок экрана показывает отказ по доступности аккаунта в регионе. Он не доказывает,
что прокси не работает: клиентский допуск и сетевой маршрут проверяются отдельно.

## Что проверено

- Установлен Manager с `resources/app.asar` и `resources/bin/language_server.exe`.
- В backend найдены восемь согласованных упоминаний `ineligible`/`ineligible_tiers`
  в protobuf-дескрипторах и Go struct tags. Прежний DevProxy их не изменял.
- `AGY_PROXY_URL` не подтверждён как настройка штатного Manager. Запуск передаёт
  стандартные HTTP/HTTPS переменные; `AG_LS_PROXY` передаётся для совместимости
  с backend, уже подготовленным внешним инструментом.
- Переданные ранее Chromium-флаги DoH не обеспечивали использование DNS Dagami
  в Go backend. Они удалены. DNS применяется в локальном мосте, независимо от Electron.
- `dns.dagami.ru` вернул `185.149.145.6` для `cloudcode-pa.googleapis.com`
  и `daily-cloudcode-pa.googleapis.com`.
- Запрос upstream proxy `CONNECT 185.149.145.6:443` получил HTTP 403.
- CONNECT через upstream по исходным именам успешно прошёл TLS-проверку;
  оба запроса `loadCodeAssist` без токена вернули HTTP 401.
- Прямые соединения через адрес Smart DNS с исходным SNI также прошли проверку
  сертификата и получили HTTP 401 на обоих хостах. Исправленный мост подтвердил
  по одному такому туннелю для каждого хоста.

401 в этих проверках ожидаем: учётные данные Google не отправлялись. Результат
подтверждает маршрут и доверенный TLS, но не доступ конкретного аккаунта и не ответ модели.

## Изученные проекты

Из [confeden/Antigravity](https://github.com/confeden/Antigravity) изучены материалы
на коммите `94663a7d3aa8a502617fb3a83d66d840f21a771d`, включая работу с backend,
ASAR, маршрутизацией и DNS. Практические выводы: разделять клиентский допуск и
маршрут, сохранять TLS сквозным, ограничивать DNS двумя рабочими хостами,
проверять результат фактического соединения и корректно сообщать об отказах.

Указанное [зеркало open-antigravity-patcher](https://gitcode.com/gh_mirrors/op/open-antigravity-patcher)
было недоступно. Исходный GitHub-репозиторий AvenCores отвечал 404; архив SourceForge
также не удалось получить. Из доступного индексированного фрагмента авторского
`source/patcher/manager/patcher.py` изучены правила `Gate`: уникальная сигнатура,
отличение подготовленного состояния, отказ при неизвестной версии и неоднозначности.
Полный код второго проекта в этой сессии не изучен.

Реализация в DevProxy самостоятельная: сторонние программы не запускались,
код этих проектов в приложение не включён, сторонние встроенные ключи не используются.

## Подготовка и откат

Подготовка предназначена для Manager с указанной структурой backend. Все восемь
контекстных сигнатур должны совпасть ровно один раз до изменения данных. Имена
метаданных заменяются на равные по длине; окружающие байты и размер файла сохраняются.
Эта операция не добавляет серверные права, подписку или доступ к платным моделям.

Оригинал сохраняется рядом с backend; манифест хранит исходный и итоговый SHA-256,
версию, размер и количество изменений. Запись атомарная. Откат разрешён только для
файла с ожидаемым итоговым SHA-256 и проверенным оригиналом. Если приложение обновилось,
старая копия его не перезапишет. Перед изменением клиент должен быть закрыт.

Проверки на временных фикстурах прошли: уникальность сигнатур, отказ для неизвестного
или неоднозначного файла, целостность копии, повторная подготовка без дополнительных
изменений, точный откат, отказ откатывать чужое обновление и ограничение DNS-маршрута.

Автоматическая проверка разрешений отклонила применение подготовки к установленному
backend без отдельного явного разрешения пользователя. Реальный клиент в этой сессии
не изменён. После разрешения можно применить подготовку и проверить вход в аккаунт.

## Ограничения

- Серверный отказ по региону, тарифу или аккаунту остаётся серверным решением.
- Штатный внешний браузер для OAuth может использовать собственный сетевой маршрут.
- DNS-маршрут использует UDP/53; TLS до Google проверяется отдельно.
- В режиме Smart DNS прямой маршрут применяется только к двум хостам выше.
  При его ошибке мост возвращает 502, а не выбирает обычный Google IP скрытно.
- Работа моделей после подготовки требует проверки в пользовательской сессии.
