# Руководство для авторов форков

Документ описывает дерево исходников после очистки 0.5.0 beta. В теге
`v0.5.0-beta` ещё присутствует старый Python/Tk-клиент; актуальная разработка
настольного клиента ведётся в `src/`, `cmd/` и `internal/`.

[README](../README.md) · [Инструкция пользователя](USER_GUIDE.md) ·
[Правила исходников](../SOURCE_POLICY.md)

## Состав и границы проекта

| Часть | Где находится | Технология и назначение |
| --- | --- | --- |
| Windows-клиент | `src/` | C#, WinForms, .NET Framework; запуск, мост, интеграции, DNS, обновления |
| Переносимый клиент | `cmd/dagami/`, `internal/desktop/`, `internal/portable/` | Go; AppKit, GTK 3 или Win32 через системные API |
| Управляемый шлюз | `cmd/dagami-gateway/`, `internal/managed/` | Go; HTTPS CONNECT, привязка устройств и проверка подписей |
| Telegram-интеграция | `deployment/managed/` | Python-адаптер и патчи к существующим боту и контроллеру |
| Отчёты | `bug_reports/` | Отдельный Python-сервис и публичные страницы |
| Сборка и упаковка | `cmd/dagami-build/` | Go; сборки, ZIP, SHA-256, аудит индекса |
| Проверки Windows | `tests/native/`, `tools/run_native_checks.py` | C#-фикстуры, расширенный Python-раннер |

Интерфейс настольного клиента нативный. Веб-страницы в `bug_reports/public/`
относятся к отдельному сервису поддержки. Rust сейчас не является зависимостью
сборки. Python нужен серверным компонентам и части тестов; для сборки клиента
он не требуется.

## Получение исходников и первая сборка

Создайте Fork на GitHub, затем используйте адрес своего репозитория.

```sh
git clone https://github.com/YOUR_NAME/YOUR_FORK.git
cd YOUR_FORK
git remote add upstream https://github.com/j46871417-ui/Dagami-Agent-Proxy.git
git switch -c docs-or-feature
```

Нужны Git и Go 1.23+. Для WinForms требуется Windows с системным компилятором
.NET Framework; для запуска интерфейса Linux — GTK 3. На macOS используются
системные AppKit и Keychain. Для сетевых секретов Linux нужны Secret Service
и `secret-tool`. Точная версия Go-зависимостей закреплена в `go.mod`/`go.sum`.

Обычная сборка для текущей системы:

```sh
go run ./cmd/dagami-build -test -source
```

В Windows для WinForms EXE и выбранных проверок:

```powershell
go run ./cmd/dagami-build -test -source -windows-native -native-checks
```

Кросс-сборка Windows x64, macOS Intel/ARM64 и Linux x64/ARM64:

```sh
go run ./cmd/dagami-build -target all -test -source -out dist-portable/fork
```

На Windows полный Windows-пакет использует WinForms. С macOS/Linux цель Windows
собирает переносимый Win32-клиент; она не заменяет сборку WinForms на Windows.
Кросс-компиляция не проверяет работу интерфейса на целевой ОС: перед релизом
проверьте каждую заявленную платформу на ней самой.

Пакеты, `dagami-desktop-source.zip` и `SHA256SUMS.json`/`.txt` появляются
в каталоге `-out`. ZIP исходников содержит настольный код и инструкции;
для серверных компонентов и истории используйте полный Git-репозиторий.

## Что менять при выпуске самостоятельного форка

Встроенные адреса относятся к инфраструктуре Dagami. До публичного выпуска
определите свои сервисы и явно укажите пользователю, куда приложение обращается.
Ни ключи доступа пользователей, ни серверные секреты не входят в исходники.

| Настройка | Файлы и замечания |
| --- | --- |
| Название и версия Windows | `src/Brand.cs`: имя, отображаемая версия, `ReleaseTag`, assembly-версии и информационная версия |
| Версия Go и имя Windows ZIP | `internal/buildinfo/version.go`; сборщик берёт тег отсюда |
| Иконки и логотип | `assets/`, ресурсы в `cmd/dagami-build/main.go`; сохраняйте имена ресурсов, ожидаемые `Brand.LoadImage/LoadIcon`, либо меняйте обе стороны |
| macOS bundle | `cmd/dagami-build/main.go`: `Info.plist`, bundle ID, имя `.app`; также проверьте строки интерфейса в `internal/desktop/` |
| Бот и bootstrap-шлюз | `src/ManagedAccess.cs` и `internal/managed/client.go`: ссылки бота, bootstrap, резервный адрес и соответствующее имя/порт |
| Обновления Windows | `src/NativeUpdates.cs`: `Repository`; валидация URL и имён assets должна остаться согласованной с вашим репозиторием и пакетами |
| Отправка баг-репортов | `src/BugReports.cs`: `Site` и `Endpoint`; сервер, страницы и конфигурация в `bug_reports/` |
| DNS-провайдеры | `src/DnsProviders.cs`, `src/SimpleUi.cs`, `internal/portable/` и `src/SystemDns.ps1`; найдите адреса, профили и проверки доверенных имён перед изменением |
| Состояние и ключи ОС | Windows: `src/DevProxyApp.cs`, `src/ManagedAccess.cs`, `src/LicenseManager.cs`; Go: `internal/portable/`. Отдельные каталоги форка требуют продуманной миграции |
| Документация и ссылки поддержки | `README.md`, `docs/`, остальные руководства, строки UI и серверные шаблоны |

Перед выпуском найдите оставшиеся обращения к инфраструктуре оригинала:

```sh
git grep -n -E 'dagami\.ru|bright26bot|j46871417-ui|45\.86\.65\.240'
```

Это поиск известных адресов, а не полный аудит брендинга и исходящих запросов.
Не меняйте идентификаторы протокола, форматы подписи, энтропию шифрования или
каталоги состояния массовой заменой текста: можно потерять совместимость
и доступ к сохранённым секретам. Тестовые ожидания меняйте вместе с реализацией.

Для стенда новый процесс клиента может получить адрес вашего шлюза через
`DAGAMI_MANAGED_URL`. Например, в PowerShell перед запуском:

```powershell
$env:DAGAMI_MANAGED_URL = 'https://gateway.example:9443'
.\DagamiAgentProxy.exe
```

Это адрес вашего сервиса с доверенным TLS, а не адрес для вставки в поле
обычного прокси. Переменная не переписывает уже сохранённую привязку.
В публичной сборке задайте собственный bootstrap; резервное соединение по IP
должно сохранять проверку TLS на правильное имя. Случайный IP вместо hostname
в HTTPS URL для этого не подходит.

## Собственные бот и шлюз

Если форку достаточно пользовательских прокси, отдельный управляемый шлюз
для их передачи не нужен. В Windows при этом отдельно остаётся политика
первичной активации; определите её для своего продукта и опишите пользователям.

Для управляемого доступа требуются ваш HTTPS-шлюз, бот выдачи кодов и система
проверки прав/маршрутизации трафика. Текущий шлюз использует существующий
loopback-вход HAProxy и контроллер. В `deployment/managed/` находятся адаптеры
и патчи к конкретному внешнему стеку, а не полный автономный Telegram-бот
с биллингом. Применимость патчей проверяйте на своей версии исходников.

Сборка шлюза из корня:

```sh
go build -trimpath -o dagami-gateway ./cmd/dagami-gateway
```

Параметры запуска описаны в `cmd/dagami-gateway/main.go`, пример unit и окружения —
в `deployment/managed/`. Нужны отдельное закрытое состояние, TLS-сертификат,
локальный upstream, секрет моста и приватный Unix-сокет для бота.
Производственное развёртывание unit рассчитано на Linux/systemd.

Бот выдаёт ограниченный по времени код, клиент создаёт ключ устройства,
шлюз регистрирует публичный ключ. Последующие запросы подтверждаются подписью
устройства. Обычные upstream-логины и пароли пользователю выдавать не требуется.
Это не защита от владельца локальной системы, имеющего доступ к ключу
или работающему локальному мосту. Сохраняйте отзыв устройств и серверную
проверку доступа. [Протокол и развёртывание](../MANAGED_ACCESS.md).

Офлайн-лицензии — отдельный механизм. Верификатор подписанных `DAGAMI2`
подготовлен, но production-ключ издателя в оригинале не настроен, а совместимость
с прежними контрольными суммами включена. Не описывайте её как завершённую
криптографическую защиту лицензий. Для собственного издателя следуйте
[контракту миграции](../SIGNED_LICENSES.md); закрытый ключ не должен попадать
в клиент, Git, исходный ZIP или тестовые фикстуры.

## Проверки перед изменениями и релизом

Проверьте `AGENTS.md`, затем выполните:

```sh
go test ./...
go vet ./...
```

Для изменений маршрутизации отдельно проверьте вариант без DNS и инспекции:

```sh
go run ./cmd/dagami-build -target all -routing-only -test -out dist-portable/routing
```

Для Windows после сборки можно запустить расширенные безопасные фикстуры:

```powershell
python tools/run_native_checks.py --assembly dist-portable/native-next/DagamiAgentProxy.exe --output-dir "$env:TEMP/DagamiForkChecks"
```

Укажите путь к своему собранному EXE, если использовали другой `-out`.
Раннер использует выделенный каталог и сохраняет результаты. Он не включает
проверки реальной активации и установку обновления. Подробности и ограничения —
в [описании Windows-тестов](../tests/native/README.md).

Используйте временные профили, loopback-серверы и тестовые процессы. Реальные
аккаунты, установленные IDE, DNS/NRPT и чужие ярлыки не должны становиться
расходным материалом тестов. Изменения серверных компонентов проверяйте
их собственными тестами; тесты адаптеров требуют подходящего снимка внешнего
стека, описанного в `MANAGED_ACCESS.md`.

Перед коммитом добавьте только нужные файлы в индекс и выполните:

```sh
git diff --cached --check
go run ./cmd/dagami-build audit
```

Аудит читает staged blobs: наличие файла только в рабочей папке недостаточно.
Он проверяет обязательные пути, дубликаты, запрещённые файлы и известные
форматы секретов. Локальный hook включается через
`git config core.hooksPath .githooks`. Не добавляйте в Git бинарники, ключи,
токены бота, пользовательские базы и приватные журналы.

## Упаковка и публикация

1. Согласуйте версии C# и Go, тег, release notes и changelog. Для beta используйте
   SemVer-тег наподобие `v0.5.1-beta`; номера здесь приведены как пример.
2. Пересоберите в отдельный `-out`, выполните проверки и проверьте содержимое ZIP.
   После добавления C#-файла обновите `nativeSources` в сборщике. Новые ресурсы
   и документы добавляйте в соответствующие списки упаковки.
3. Для встроенного Windows-обновления публикуйте `DagamiAgentProxy.exe`,
   `Dagami-Agent-Proxy-<тег>-windows.zip` и `SHA256SUMS.json` из одного прогона.
   Внутри Windows ZIP сборщик создаёт `SHA256-native.json`. Не переименовывайте
   assets без изменения строгой проверки в `NativeUpdates.cs`.
4. Добавьте пакеты macOS/Linux, ZIP исходников, `SHA256SUMS.txt`, описание
   изменений и ограничения проверок. Опубликуйте beta как предварительный релиз.
5. В GitHub Actions сборки запускаются вручную через workflow **Dagami Agent
   Proxy (manual builds only)**. Артефакты Actions сами по себе не создают Release.
   Workflow **Source hygiene** проверяет изменения и историю на секреты.

Windows можно подписать собственным сертификатом через флаги `-sign-tool`,
`-sign-thumbprint` и `-timestamp-url`. Сборщик проверяет подпись до упаковки.
Подпись и нотаризация macOS в текущем сборщике не автоматизированы. Измеряйте
ложные срабатывания на готовых пакетах; обещать их отсутствие нельзя.
[Вариант Routing и подпись](../APP_ROUTING.md).

Перед распространением проверьте, что ваш updater получает релизы вашего форка,
отчёты уходят на ваш сервер, а ссылки поддержки ведут к вам. Не размещайте
приватные административные маршруты сервиса отчётов на публичном интерфейсе;
схема администрирования описана в [BUG_REPORTS.md](../BUG_REPORTS.md).

В корне находится [MIT License](../LICENSE). Сохраняйте предусмотренные ею
уведомления об авторстве и лицензии при распространении. Для компонентов

лицензию purego в соответствующие бинарные пакеты.

Оставляйте понятную историю изменений и собственный канал поддержки.
Для получения upstream-изменений выполните `git fetch upstream` и изучите diff
перед объединением. Особенно внимательно переносите изменения транспорта,
проверок подписей, TLS, отката и установщика обновлений; не заменяйте их
старыми копиями при разрешении конфликтов.
