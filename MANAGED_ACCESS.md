# Доступ Dagami через Telegram

Рабочий HTTPS-адрес управляемого шлюза `https://test-dns.dagami.ru:9443`.
На период перехода старый вход на 50128 обслуживает ранее выданные реквизиты.

## Подключение устройства

1. Отправьте `/key` в `@bright26bot`. После проверки доступа бот выдаст ключ
   формата `DAGAMI1-…` на 15 минут для одного устройства.
2. Вставьте ключ в окно активации или откройте «Подключение → Подключить по
   ключу». Dagami получит адрес по `GET /v1/config`, сохранит ключ устройства
   P-256 в хранилище ОС и включит общий маршрут. Доступно три устройства
   на аккаунт. Повтор на том же устройстве работает до истечения ключа.

При сбое системного DNS встроенный адрес можно открыть по резервному IP.
Клиент проверяет сертификат на имя шлюза и подписывает запросы для этого
имени. Администратор может задать другой шлюз через `DAGAMI_MANAGED_URL`.
Прежняя привязка по ссылке поддерживается. Для старых клиентов бот
выдаёт офлайн-лицензию кнопкой «Ключ для старой версии» и командой `/license`.

В Windows на вкладке «Подключение» можно ввести HTTP/HTTPS-адрес или
`host:port` и нажать «Использовать свой прокси». Адрес хранится отдельно
от ключа устройства. Кнопка «Использовать Dagami» возвращает к уже
привязанному маршруту. Для системного VPN укажите `direct`.

Для каждого соединения Dagami подписывает адрес шлюза, метод, назначение,
время и случайный nonce. TLS проверяется по системным корням доверия. Публичный
шлюз принимает только подписи зарегистрированных устройств, отклоняет Basic
и повторы. При запуске из Dagami или настроенного ярлыка приложение получает
один и тот же выбранный маршрут через локальный мост. Клиентские приложения
должны поддерживать прокси. Сервис, выбранный на вкладке «Диагностика»,
определяет адрес тестового запроса. В режиме
управляемого доступа WinForms не отправляет целевой трафик через Smart DNS.

В меню бота можно отозвать все устройства. Отзыв закрывает текущие туннели
на управляемом шлюзе. Подписки, блокировки, маршруты, список доменов и учёт
трафика продолжают проверяться действующим контроллером при новом CONNECT.
Существующие туннели при изменении подписки ограничены таймаутом шлюза.

Подпись доказывает владение ключом установки. Локальный пользователь с доступом
к хранилищу ключа или к loopback-мосту может использовать их из другого процесса.
Ограничение удалённого доступа реализуется регистрацией ключа и отзывом.

## Подготовка на сервере

Сборка шлюза из корня репозитория:

```text
go build -trimpath -o dagami-gateway ./cmd/dagami-gateway
```

- Выделите отдельный каталог состояния с правами 0700 и один экземпляр шлюза.
  Реестр устройств хранится в `devices.json`. Одноразовые коды и nonce
  хранятся в памяти. После перезапуска незавершённая привязка начинается заново.
- Используйте доверенный TLS-сертификат на публичном HTTPS-входе. TLS и HTTP/1.1
  CONNECT должны доходить до процесса шлюза. Настройте синхронизацию часов.
  Unit загружает цепочку, закрытый ключ и секрет через `LoadCredential`.
  Если сертификат обновляется Certbot, привяжите перезапуск шлюза к deploy-hook
  нужного сертификата. Исходные файлы могут оставаться доступными только root.
- Шлюз подключается к действующему HAProxy на отдельном **loopback**-адресе.
  Выдайте шлюзу и контроллеру один случайный секрет из 32 байт в base64url
  без `=` через файл с ограниченным доступом. Шлюз передаёт его только
  локальному HAProxy. Учётка и политика берутся из текущего реестра прокси.
  В HAProxy выделите прямой HTTP-вход на `127.0.0.1:9444` без `accept-proxy`.
  Разрешите заголовок `Dagami-Local` только на этом входе и отклоняйте на нём
  Basic до вызова Lua-авторизации. Оставьте действующие правила доменов и
  backend учёта трафика. Ограничение старого входа по IP не переносите на
  loopback, где все клиенты шлюза имеют один адрес.
- Бот обращается к `/private/issue-access`, `/private/pending`,
  `/private/approve` и `/private/revoke` через Unix-сокет. Доступ к каталогу
  и сокету имеют только служба шлюза и бот. Публичный HTTPS-вход принимает
  выданный код на `POST /v1/redeem` с подписью устройства.
- Шлюз хранит хеши новых кодов в памяти. После перезапуска выдайте новый
  код для незавершённой активации. Привязанные устройства остаются в реестре.

Пример service-файла и адаптеры находятся в `deployment/managed`. Патчи сверены
с локальным снимком работающего стека от 7 ноября 2026 года. Сначала
сравните их с текущими исходниками через `git apply --check` и сохраните
копии исходников, конфигурации и SQLite. Файлы привязки TLS и секреты берите
из закрытой конфигурации сервера. Патчи применяются в каталогах `/opt/agw-bot`
и `/opt/agw-gateway` соответственно. `bot_access.py` размещается рядом с меню.
После распаковки серверного ZIP установите `dagami-gateway` с правами 0755.

В существующем `frontend agw_entry` добавьте локальный `bind` и ограничьте
тип авторизации до `http-request lua.agw_auth`. Правила блокировки доменов
должны по-прежнему выполняться перед авторизацией.

```haproxy
    bind 127.0.0.1:9444
    acl managed_ingress dst_port 9444
    acl managed_auth req.hdr(Proxy-Authorization) -m beg "Dagami-Local "
    http-request deny deny_status 407 if managed_ingress !managed_auth
    http-request deny deny_status 407 if !managed_ingress managed_auth
```

В unit контроллера загрузите тот же root-only файл через
`LoadCredential=managed-bridge-key:/etc/dagami-managed/bridge-key` и передайте
`DAGAMI_MANAGED_BRIDGE_KEY_FILE=/run/credentials/agw-controller.service/managed-bridge-key`.

| База патча | SHA-256 файла снимка с LF |
| --- | --- |
| `dagami_menu.py` | `1f4f734a8c7f8f9ca9d17a71fe73ff43a08172a9884bebb6ec230012beeaeac3` |
| `controller.py` | `f939a74a2a49097e7e06cf86401366df956baac97e13915949b0998967b5aa73` |

Для тестов адаптеров укажите путь к этому снимку в `DAGAMI_BOT_SNAPSHOT`.
Нужны `agw-bot/dagami_menu.py`, `agw-gateway/controller.py` и
`agw-gateway/traffic_meter.py`. Хранить пользовательские базы или секреты
в локальном снимке для тестов не требуется.

## Переход на привязку

1. На стенде запустите шлюз и патченый контроллер. Проверьте привязку,
   CONNECT через текущую политику, `403` для запрещённого назначения, отказ
   после отзыва и отображение учёта трафика. Проверьте приватность сокета.
2. Запустите публичный HTTPS-вход и проверьте подпись, TLS и отказ по Basic.
   При поэтапном переходе `DAGAMI_MANAGED_ALLOW_LEGACY=1` сохраняет работу
   прежних учёток через старые входы. Приватный вход шлюза принимает только
   `Dagami-Local`. Переменная относится к контроллеру.
3. Включите меню привязки и передайте боту `DAGAMI_MANAGED_URL` для справки.
   Бот создаёт внутреннюю учётку при подтверждении устройства. Пользователь
   видит результат привязки, лицензию и лимит трафика.
4. После распространения клиента с поддержкой привязки уберите
   `DAGAMI_MANAGED_ALLOW_LEGACY=1` и прежние публичные Basic-входы.
   Проверьте отказ по ранее выданному паролю и недоступность старого порта
   HAProxy извне.
5. Откат возвращает конфиги и код из сохранённой копии. Перед возвратом
   публичного Basic оцените ранее выданные реквизиты. Базы трафика и учёток
   сохраняйте отдельно от кода.
